## Goal and intended experience

Elvis, Dailos and the team use the Gestor standing up and in a hurry. After this round:
- every screen reads at a glance (Hoy does not grow without end, upcoming events use the full width, the calendar copes with many venues, hours are never cut);
- conflicts are resolved from the warning itself, with a preview of the chain and a signed confirmation, and tasks can be moved on the calendar by long-press;
- there is one place to see every task, and dependencies are visible;
- open questions get answers; materials get photos;
- money lives where an event manager expects it: taxes per company, fair comparisons with medals, a simple and good-looking event budget with expenses, offers with validity, versions and renegotiation;
- access is personal and private: username + password, own profile, password recovery by e-mail, roles that the server enforces, an audited support session instead of a master password;
- the brand reads «Ox Eye» everywhere a person looks, and downloaded PDFs have names that make sense.

## Product decisions confirmed by the user (2026-11-27)

- Administrators: Yeray, Elvis, Dailos, Fabián (new seed user). Developer role sees budgets (a separate permission, easy to withdraw). Roles are per organization; one account can hold several roles (Fabián: administrator + developer).
- «Equipo» is the shared team account: display name and team photo, password set by a developer/administrator, no recovery e-mail. «Invitado» is read-only: no profile, cannot change its password; a developer sets it.
- Developers (and administrators) can set a **provisional** password for any account to unblock someone fast. They never see the current one; the user must replace a provisional password before reaching sensitive information.
- Password recovery by e-mail: if the user has a verified personal e-mail, the reset link goes there (standard flow). Otherwise it goes to the project inbox (configured in `server/.env`, never written in the repository), and the developer passes it on. Mail is sent from the project account through SMTP.
- Budget: one total per event + a list of expenses (concept, company, optional linked offer, amount before tax, tax, planned / confirmed). Shows budget, planned and confirmed. No invoices or payments. It must look attractive, in the Gestor's editorial style.
- Tax: picked from a list (IGIC, IVA, otro, ninguno, sin saber) with an editable percentage prefilled (7 % / 21 %) and marked «por verificar» until confirmed; an offer may override its company's tax; old offers get no invented percentage.
- Only administrators approve an offer received from a supplier.
- Material images: one main + up to four more, resized on the device (~1600 px, < 400 KB), stored in PostgreSQL.
- «Mantener ambas» in a conflict requires a short reason; the warning becomes «aceptado» and stays in the day close.
- Invitado: no Contactos or Catálogo (server denies too); on a task sees the company name, not openable, no contact; search returns no contacts, companies or offers; day close shows counts only; work orders unchanged (already withheld).
- Brand: «Ox Eye» in all user-facing text; «OxEye» only for technical identifiers; «Ojo de Buey» removed from the product. The `ojo-de-buey` project format and storage key stay (saved projects must keep opening). Old code comments stay. `CLAUDE.md` is protected: the AI Lead proposes the text, the user installs it.
- Ideas for later accepted into this round: e-mail sending (accounts only: recovery and verification) and «Ver como Invitado». Kept for later: TOTP second factor (needs QR enrolment and more time than we have before 2/12) and a day close covering several days.
- Supplier quote requests are still sent by hand from the user's own e-mail (mailto with the personal link), not by the server. Nothing is sent to a company without the user's confirmation.

## Technical decisions

- Contracts first: the AI Lead writes the shared types and permissions in `shared/logistics/` before dependent work (`architect` reviews once: roles, taxes, budget, offer versions, images, answers, venue hours).
- Migrations `0007+`, append-only, additive (new tables / nullable columns); tested from empty and from a 0006 database with data.
- Mail: `server/src/mail/` behind an interface; a console transport for tests and when SMTP is not configured (the link is logged only in development, never in production). SMTP settings in `server/.env` (`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `MAIL_FROM`, `RECOVERY_FALLBACK_EMAIL`), placeholders in `server/.env.example`. Links built from the request origin validated against `CORS_ORIGINS` (or `PUBLIC_APP_URL` when set).
- Images in a `media` table (`bytea`, content type, size, owner record); served through authenticated routes with caching headers; profile photos reuse it.
- Permission checks in one server module; redaction extended so the device cache and outbox withhold exactly what the API does (as `redaction.ts` today). Route-surface test updated for every new route.
