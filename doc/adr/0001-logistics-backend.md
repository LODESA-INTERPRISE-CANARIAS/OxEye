# ADR 0001 · Logistics Manager backend

|            |                                                                                                             |
| ---------- | ----------------------------------------------------------------------------------------------------------- |
| Status     | Accepted (2026-11-26, plan `gestor-logistico`)                                                              |
| Scope      | `server/`, `shared/logistics/`, `src/logistics/`                                                            |
| Supersedes | The OX-era ADR-024-001/002/005 (removed in `pivot-cleanup`); their still-valid rules are carried over below |

## Context

The Logistics Manager is a real multi-user tool: several people capture and consult the same data from phones and PCs, sometimes without coverage. The simulation stays browser-only. The team (two developers) must run everything on a laptop today and move it to an external server later without rewriting it. The repository is public and `main` is published on GitHub Pages.

## Decision

1. **One small service** in `server/` (Node + TypeScript), modules by domain, a thin HTTP layer (Hono) over plain functions. Node 26 runs TypeScript directly; no build step. Configuration only from environment variables.
2. **PostgreSQL is the authority** for shared logistics data. The browser keeps only a cache, drafts and an outbox (Dexie); `localStorage` keeps preferences and the session token.
3. **Versioned SQL migrations** in `server/migrations/`, forward-only, each applied in a transaction and recorded in `schema_migrations`. An applied migration is never edited. A destructive migration needs the user's explicit approval.
4. **Identifiers** are UUIDs, never array positions.
5. **Time**: instants as `timestamptz` (UTC); each organization and event stores its IANA time zone, `Atlantic/Canary` by default. Local ↔ UTC conversion lives in `shared/logistics/time.ts`.
6. **Optimistic concurrency**: mutable records carry `version`; a stale write is rejected with 409 and the current record, never applied silently.
7. **Provenance**: mutable records carry author, timestamps, `source` (observed / reported / document), `verification` (draft / to verify / validated) and `is_demo`; every write appends to `activity_log` in the same transaction.
8. **Validation** at the API boundary (zod), with Spanish messages for the UI.
9. **Auth for the pilot**: five named users with passwords hashed with `crypto.scrypt`; opaque session tokens (only their SHA-256 is stored) sent as a Bearer header; sliding expiry; login rate limit per name and per client IP (each attempt is counted before the password is verified, so parallel requests cannot bypass it; behind a proxy the client IP is the X-Forwarded-For entry `TRUST_PROXY` hops from the right, never the client-controlled left-most one); `guest` role is read-only. Initial passwords are generated by the seed and never committed.
10. **Secrets** only in an untracked `server/.env`; `server/.env.example` is committed with placeholders.
11. **Sensitive data**: the API serves no simulation data; Punto Violeta cases are never stored centrally.
12. **Shared contract** in `shared/logistics/` (types and pure functions, no package imports) used by both sides, so the frontend build never depends on server packages.
13. **Tests** run without Docker against PGlite (PostgreSQL compiled to WASM, in-process).
14. **Deployment**: `server/Dockerfile` + compose profile `full`. Moving to the external server means the same image plus a `.env` and a managed or containerised PostgreSQL in an EU region, with daily backups and a tested restore.

## Alternatives considered

- Backend-as-a-service: faster start, but vendor lock-in and row-level security to learn under time pressure.
- SQLite on the server, reusing the old Drizzle schema: weak concurrent writes; the schema mirrored the scene JSON, not the domain. Drizzle was removed.
- An ORM: more to learn and generate; plain SQL with a 40-line adapter is enough at this size.

## Consequences

- No build step and few dependencies (hono, @hono/node-server, zod, postgres; PGlite for tests).
- Docker and the running server are operated by the user; Claude Code tests against PGlite.
- Hosting, backups and TLS are decided when the external server is chosen; this ADR is updated then.
