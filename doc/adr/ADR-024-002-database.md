## Context

Verified persistence in v0.16.0 (commit `a4f1213`):

| Store | Content | Role today | Evidence |
|---|---|---|---|
| `localStorage['ojo-de-buey-project-v1']` | Whole `ProjectFile` JSON (`version: 1`) | **De facto authority** | `src/db/repository.ts:27,125-186` |
| `localStorage['ojo-prefs']` | UI preferences | Per-device preferences | `src/db/repository.ts:28,193-224` |
| Dexie `OxEyeDatabase` v1: `projects`, `simulationRuns` | `projects` gets the same JSON under id `active`; `simulationRuns` unused | Write-only copy | `src/db/repository.ts:47-58,176-184` |
| Drizzle SQLite schema (`projects`, `scenes`, `annotations`, `contacts`, `companies`, `simulation_runs`) | — | Not used at runtime; only re-exported by `src/index.ts:16` | `src/db/schema.ts` |
| `Ojo_de_Buey_Proyecto.json` | Export/import of the whole project | Only way to share | `src/db/repository.ts:292-351` |

Further facts:

- Only `version === 1` is accepted; there is no migration chain. Invalid stored data is silently replaced by a default project (KI-07).
- Identifiers are partial: many items get `crypto.randomUUID()` on creation (contacts, inventory items, ballast, new fences and other map elements), but legacy fences without id receive `'fence-' + i` on load (`src/db/repository.ts:77-78,144-145`), scenes are keyed by venue (`cristo`, `constitucion`, `vega`), and projects and events have no id.
- Dates are free strings (`eventDate`, `startDate`, `endDate`, `endTime`); there is no explicit `Atlantic/Canary` handling.
- Geometry is stored in local metric coordinates per venue map, with UTM EPSG:32628 used for georeferencing.

## Options considered

| Option | Pros | Cons |
|---|---|---|
| **PostgreSQL (+ PostGIS evaluated)** | Relational integrity across the entities of the authority map; transactions for multi-entity writes (VAL-CORE-TRANSACTION-001); exclusion constraints for overlapping reservations (`tstzrange`, INV-005); mature spatial extension; available self-managed, managed and in BaaS (ADR-024-001 B and C) | Operational knowledge needed if self-managed |
| SQLite on a server (reusing the Drizzle schema) | Simple; schema exists | Weak concurrent writes; the existing schema mirrors the scene JSON, not the domain entities; no spatial or range types comparable to PostGIS / `tstzrange` |
| Document store (e.g. one JSON per project) | Close to today's model | Reproduces today's problem: one blob, no per-entity ownership, no relational integrity (contradicts INV-003, INV-006) |

## Decision (recommended)

1. **PostgreSQL is the authoritative store** when a server exists (ADR-024-001). Hosting in an **EU region**.
2. **PostGIS:** evaluated, not decided here; the decision belongs to ADR-024-003 (cartography). Until then, geometry may be stored as structured JSON in local metric coordinates plus the venue's reference system, as today.
3. **Schema per owner domain** (one schema or table prefix per domain of the authority map). A domain's tables are written only by its module.
4. **Identifiers:** UUID for every entity, generated by the client or server; never derived from array position. Legacy imports get deterministic ids (see transition strategy) so re-imports do not duplicate (INV-019).
5. **Versioning:** each mutable aggregate carries a `version` integer used for optimistic concurrency; stale writes are rejected, never silently applied (INV-004).
6. **Time:** instants stored as `timestamptz` (UTC); each event stores its time zone (`Atlantic/Canary` by default) for display and day boundaries (TEC-006).
7. **Migrations:** versioned SQL migrations in the repository, applied per environment (development, pilot). Each migration is reviewed; destructive migrations require explicit approval.
8. **Backups and restore:** daily backup with at least 7-day retention and a documented, tested restore (INV-015, MST-E2E-006). Implementation belongs to OX-21.
9. **Browser storage after the server exists:** Dexie becomes cache plus drafts (ADR-024-005); `localStorage` keeps only preferences. Neither is authoritative for shared data (TEC-007).
10. **Drizzle SQLite schema** (`src/db/schema.ts`) is **not** the target model. Removing it and the `drizzle-orm` dependency is proposed as a follow-up (OX-21 / OX-24), not done here.
11. **Secrets** (database credentials, service keys) live only in server configuration; never in SPA code, exports or the repository (INTG-009).
12. **Sensitive data:** Punto Violeta records (`sensitive: true`) and personal data are stored only after an explicit privacy decision (INV-018). Until then, see the data authority map: sensitive real-incident data is not persisted centrally.

## Environments, security, operation, cost (conditions from §24.145)

| Condition | Position |
|---|---|
| Environments | `development` (local, Docker or provider branch) and `pilot`. No production claims during the pilot. |
| Migrations | Versioned SQL; forward-only; rehearsed on a copy before the pilot DB. |
| Security | TLS only; least-privilege DB roles per module; no public DB access; server-side authorization (INV-011); row-level isolation by organization (INV-002). |
| Operation | Backups + restore drill (OX-21); monitoring of disk and failed jobs; named operator in OX-24 responsibility matrix. |
| Cost | See the estimate in [ADR-024-001](ADR-024-001-physical-architecture.md#cost-estimate-indicative-consulted-2026-11-25). |

## Consequences

- OX-21 implements the store; OX-03 adds organizations/users; OX-05 can rely on range constraints for reservation overlaps.
- The client must stop treating `ProjectFile` as the unit of persistence for shared data and move towards per-domain repositories.
- `EventDemandConfig` stays the single demand source and becomes a field of the Distribución aggregate (Venue & Layout domain), not a separate copy.

## Conditions and open points

- Server budget (ADR-024-001).
- PostGIS decision in ADR-024-003.
- Privacy decision for central storage of Punto Violeta and personal contact data (product direction + data-protection advice).
